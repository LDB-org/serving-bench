# 评测矩阵：性能、回答质量与工具调用

状态：设计提案，尚未实现。本文扩展主设计，属于首版交付范围，不表示已有题库或实测结果。

## 1. 一次评测回答什么

在指定模型、引擎配置、内容、输入输出长度和负载下：回答是否正确，工具是否用对，多久给出可用结果，Prefill/Decode 瓶颈在哪里，压力升高后是否仍然可用。

结果呈现为分项表和曲线：质量 vs 负载、TTFT vs 输入长度、生成间隔 vs 输出长度、吞吐 vs 并发、工具任务成功率 vs 并发。不同模型、量化、reasoning 设置单独分组。默认不做“综合跑分”；若业务确需加权，必须预先声明权重和覆盖范围，并保留全部分项。

## 2. 内容类型

| 场景 | 内容与变化 | 质量依据 | 主要性能观察 |
| --- | --- | --- | --- |
| 事实问答 | 中/英/混合语言，实体、日期、数值 | 标准答案、可接受别名、EM/F1 | 短请求延迟及并发 |
| 数学与逻辑 | 算术、多步推理、约束问题 | 数值/符号归一化，显式误差容限 | reasoning token、首答案时间、总耗时 |
| 代码 | 生成、补全、修复，代码块与注释混合 | 隔离单元测试，优先 pass@1 | 长输出、截断率、生成间隔 |
| 长文理解 / RAG | 单文档、多文档、干扰材料、证据位置前/中/后 | 答案正确性、证据 ID 与引用支持度 | 长输入 TTFT、缓存、上下文边界 |
| 摘要 / 翻译 | 新闻、技术文档、表格，多语言 | 固定 rubric、参考指标与可选人工/judge | 长输入输出、长度控制 |
| 结构化抽取 | JSON、日志、CSV、嵌套对象、缺失字段 | JSON Schema、字段级正确率 | 格式失败率、约束解码影响 |
| 指令遵循 | 格式、长度、必须/禁止字段、跨轮约束 | 确定性检查器，主观条件单列 | 约束复杂度与延迟 |
| 多轮对话 | 指代、信息修正、上下文累计 | 最终答案、状态一致性、每轮约束 | 每轮延迟与整段耗时 |
| 工具任务 | 单调用、并行、串行依赖、多轮恢复 | 选择、参数、执行状态、最终答案 | 首个完整调用、工具耗时、整任务耗时 |

合成随机 token 仅用于容量和长度控制，真实语料用于实际内容表现，两者不能混在质量表里。知识问答固定数据版本与答案时点；不把过期知识问题混同服务回归。多模态预留 modality 字段，但首版完整矩阵以文本为主；视觉/音频需独立输入计量与评分器后再加入。

## 3. 性能实验轴

| 轴 | 建议起始值 | 约束 |
| --- | --- | --- |
| 输入长度 | 128 / 1K / 4K / 16K / 32K tokens | 按模型上下文上限裁剪实验集合，不静默截断样本 |
| 输出上限 | 32 / 256 / 1K / 4K tokens | 记录实际输出、EOS 与 length 截断；质量模式不强制凑长度 |
| 并发 | 1 / 4 / 16 / 32 | 每个点独立运行，预算显式声明 |
| 到达率 | 用户指定固定间隔或 Poisson RPS | 记录提供、发出、拒绝、完成四种速率 |
| 缓存 | unknown / 禁用 / 不同前缀 / 故意共享前缀 | 只有证据支持才称为冷/热缓存 |
| 推理模式 | 服务默认 / 显式开启 / 显式关闭 | 不支持时跳过并记录，不能静默降级 |
| 内容 | 上表各类型 × 语言 | 各组独立统计，再按冻结权重汇总 |

Prefill-heavy：长输入、短输出；Decode-heavy：短输入、长输出；Mixed：长短请求混合，观察长输入对短请求的干扰。它们不是纯阶段 microbenchmark。内部阶段耗时以主设计中的引擎遥测为准，TTFT 包含调度、网络和首 token 生成，不能写成 Prefill time。

不默认遍历所有组合。先用一组固定代表样本 smoke，再跑单轴扫描，最后选少量业务代表组合。`plan` 应输出实际 case 数、最大请求数、token 上限估计和时间预算；不能估计的项明确 unknown。负载条件下的截断/超时仍计入质量失败。

## 4. 回答质量评分

评分优先级：确定性规则 → 已有上游评测实现 → 经校准的 judge/人工。题目携带 case_id、dataset revision/hash、语言、内容标签、输入、独立 oracle、评分器与 rubric 版本。参考答案不进入模型请求。

- Exact match、数值容差、字段级 F1、格式约束按任务定义，不用一个字符串相等覆盖所有任务。
- 代码只在一次性隔离执行环境内运行，禁网、无宿主凭据、有 CPU/内存/时间限制；隔离环境不可用则标记 unsupported，不能回退宿主 shell。
- 可选 judge 需显式配置，记录模型版本、prompt、rubric、温度和裁决；默认不向外部服务发送私有回答。配对评判隐藏候选身份、交换顺序检查位置偏差，抽样人工校准。被评回答属于不可信数据，不能获得 judge 工具或指令权限。
- 性能测量完成后离线评分；工具任务中的工具执行属于 episode，自然进入整任务耗时。judge 和代码评分不能与压测争用同一目标 GPU 然后计入性能。
- 总体任务成功率分母为预先选定且支持的全部样本，超时、拒绝、无效格式、截断导致未通过均保留。另报仅成功响应的条件质量、评分完成覆盖率、unsupported 和 judge_error；评分器失败不冒充模型错误，也不能把剩余样本分数作为完整结论。
- 比较使用同一题配对差异；重复轮次按 case/episode 聚类，避免把同题重复当独立样本。区间方法、随机种子和样本量随结果保存；小样本只作 smoke，不作排行榜能力声明。

上游题库固定版本、许可证、split、few-shot、模板和评分协议。首选 [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) 可通过远程 API 执行的生成任务。Chat API 通常不具备任意 continuation loglikelihood；依赖这类能力的任务应 unsupported，不能偷偷改成选择题生成后沿用原 benchmark 名称。

上游运行产物属于独立来源；若无法经本工具事件核心测量，只导入质量证据，不把上游耗时纳入同口径性能排名。裁剪/改编集合明确标记 subset/custom；开发调参集和最终确认集分开。正式能力评测不能只选看起来会过的题。

## 5. 工具调用正确率

| 层次 | 检查 | 常见错误 |
| --- | --- | --- |
| 协议 | 流式参数片段合并、call_id、结束状态、JSON 解析 | 重复执行半截参数、串错并行调用 |
| 选择 | 应调用、应不调用、选中正确工具集合 | 幻觉工具、多余调用、遗漏调用 |
| 参数 | 必填字段、类型、枚举、取值、依赖关系 | schema 合法但业务参数错误 |
| 执行 | 返回值、状态转移、前置条件、幂等约束 | 错误对象、重复操作、顺序错误 |
| 多轮 | 接收工具结果、恢复错误、补充询问、完成目标 | 不消费结果、死循环、恢复失败 |
| 最终回答 | 与工具结果和期望目标一致 | 调用成功却编造最终结论 |

场景覆盖：单工具、多候选选一、多调用并行、依赖调用串行、无需工具、缺参数需追问、工具返回空/错误、用户多轮修正。首版用确定性内存工具（计算器、测试库存查询、临时日程状态等），每个 episode 从固定状态重置。参数只分派给注册工具，不 eval 模型输出；不调用真实邮件、支付或业务修改接口。

工具执行前等待完整可解析调用及协议确认的结束信号；并行调用按 call_id 聚合，状态依赖通过任务图校验。顺序无关任务按等价结果判定，不要求唯一调用顺序；有依赖时必须满足先后约束。

同时记录 invocation-level 和 episode-level 成功率，以 episode 成功作为多轮任务主指标，防止大量容易调用稀释一次关键失败。限制 max_turns、max_tool_calls、总 token 与墙钟预算，超限记失败。区分错误恢复测试中预期的工具异常和评测环境自身故障。

计时拆为首个完整工具调用延迟、每轮模型耗时、工具耗时、整段任务耗时；并行工具有重叠，不能把各耗时简单相加。质量约束 goodput 为“通过评分且满足全部预设任务 SLO 的 episode 数 / cohort 墙钟窗口”；评分在压测后完成，其耗时另列。

参考 [BFCL 单轮与多轮评测设计](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html)，候选接入固定版本 BFCL 的兼容任务。自定义 fixture、subset 或改动协议不能称为官方 BFCL 分数。先验证 API、chat template 和工具 parser 的兼容性，再解读模型能力。

## 6. 三种运行套件

- `performance`：合成或真实内容，做负载与长度扫描；不声称回答正确。
- `quality`：固定样本和生成预算，低负载评分，形成质量基线。
- `quality_under_load`：在指定负载下运行同一批可评分样本，比较质量、工具任务成功率与 SLO。多轮工具任务的并发单位是 episode，HTTP 在途请求另有上限；open-loop 调度 episode 到达，后续轮次按依赖串行产生，不伪装成固定 HTTP RPS。

原生 tools、JSON 文本模拟调用、约束解码分别成组；streaming 与 non-streaming 也分别成组。schema 有效不代表语义正确。未知 capability 会使依赖它的 case 显式跳过，不应为了跑全而静默改 prompt。

## 7. 分阶段交付与发布门槛

M1 建测量核心，M2 同时建立质量和工具评分，M3 加负载/阶段遥测及联合报告，M4 接真实端点验收与上游桥接。M1 完成不意味着完整首版完成。

首版验收至少要求：中英内容、问答/数学/代码/结构化/长文代表任务；单轮与多轮工具任务；Prefill-heavy/Decode-heavy/Mixed；低负载与压力条件；真实端点生成记录与可复算评分。引擎遥测不足时允许黑盒评测通过，但报告不得声称已测得内部 Prefill/Decode，能力表明确显示缺项。
